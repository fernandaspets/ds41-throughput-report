1. Abstract

Two build lines of the same serving stack — same model, same four GPUs, same launch knobs, same benchmark client — differed by up to 2.8× in decode throughput: the “karmic” line managed 196 tok/s at C8 where the “jovian” line did 541 tok/s. Prefill was only ~28% down, and the deficit grew monotonically with concurrency, which ruled out a fixed overhead or a broken kernel.

The cause was not in either codebase. It was in how the karmic lane was launched. That image ships a layered configuration system (platform foundation → model profile → hardware profile → preset → explicit environment), and a raw command — running the serve script directly — bypasses profile resolution entirely. The lane therefore never received the PCIe hardware profile’s NCCL policy, NCCL selected a poor intra-node transport, and every collective cost ~4 ms instead of ~0.9 ms. With roughly two collectives per decode step, that was ~8.8 ms of a ~10.3 ms step.

Adding one variable, NCCL_P2P_LEVEL=SYS, restored the lane to 512 tok/s at C8 and, with the profile-declared graph capture size (128 instead of the 64 we had been forcing), to 542 tok/s — at or above the reference.

Three things came out of the investigation beyond the fix: a one-line upstream contract restoration worth +17% at C1; a measured map of the speculative-decoding trade-off; and a conservation law — tokens/step × steps/s is constant — which says the decode is collective-bandwidth-bound, so spec-decode tuning cannot raise throughput and only three levers can.

The shape of the gap is the first clue

  • Decode-only. Prefill was 7,552 tok/s on the slow lane versus 10,904 on the reference — a 28% deficit, not 2.8×. Whatever it was, it punished the decode step disproportionately.
  • Growing with concurrency. C1 was nearly at parity; the penalty scaled with the number of rows per step. That is the signature of something that scales with the batch payload — not of a fixed per-step overhead.
  • Both lines equally bad when graphs are off. With CUDA graphs disabled, both lanes collapsed to ~8 tok/s (section 3.5). The deficit existed only inside the graph path, so it was not host-side Python overhead.

3. Methodology

Six things, in the order they mattered.

3.1 Matched configuration or nothing

Every comparison held the model, GPUs, client, cells, capture size, speculative depth and scheduler limits identical, and changed exactly one thing. The first matched pair took a full day to construct (four boots) because we kept discovering knobs we had been silently overriding.

3.2 Elimination by measurement, not by argument

Each hypothesis was killed with numbers rather than reasoning:

  • Stale commits — a 54-commit-stale snapshot measured identical.
  • Library versions — both lines shipped the same package version; a kernel-level diff harness showed the reference and our kernels agreeing bit-exactly on quantisation, GEMM and the scheduler-side math (MXFP8 quantisation and FP8 GEMM were exactly equal).
  • The autotuner — selection caches differed for 296 of 1122 shared workloads, and reverting the suspected timing change moved nothing (189 vs 174 at C4).
  • Speculative decoding — acceptance differed by only 12%, against a 175% gap.
  • Our own patches, the model entrypoint, plan caches, breakable graphs, the PCIe flag — each measured, none responsible.

3.3 The trap that cost half a day: tests under a dominant bottleneck are void

The slow lane spent 92.7% of its GPU time inside NCCL. Every A/B we ran on that lane — library tuning, kernel selection, graph settings — was measured through a bottleneck five times larger than the effect being tested. Those results were not “eliminations”; they were unmeasured.

This is the single most transferable lesson in the report. We rebuilt the list of “void” results and re-ran the cheap ones after the fix; one of them (a b12x MoE tuning contract) turned out to be genuinely neutral, but we could not have known that beforehand.

3.4 Profile out-of-process, because the in-process profiler wedges the engine

vLLM’s PyTorch profiler was unusable here: after stop_profile the workers logged profiler_stop and then hung, rank traces stayed truncated, and a later /start_profile returned HTTP 000. Three attempts, three hangs.

We switched to nsys, which profiles out of process. Two constraints made it work: CUPTI cannot attach to a running process, so the profiler must be the parent of the engine (we re-exec the image’s own entrypoint underneath it, preserving profile resolution); and the capture is triggered through the CUDA profiler API by running vLLM’s profiler in cuda mode, so nsys records exactly the benchmark window and nothing else.

4. The solution

Not a code change: a launch change. The karmic image expects its configuration to be composed by its runtime, and its README says so plainly — raw commands bypass profile resolution. Applying the PCIe hardware profile’s NCCL policy (or, minimally, NCCL_P2P_LEVEL=SYS) is the fix.

The minimal reproducer. Same image, same knobs, same client. Add one environment variable: 
docker run … -e NCCL_P2P_LEVEL=SYS …   # C8: 196 → 512 tok/s
                                        # with capture 128: 542 tok/s

Why it works

NCCL_P2P_LEVEL selects the peer-to-peer transport for intra-node collectives. Without it, NCCL chose a path unsuited to this multi-root PCIe topology, and the cost appeared as per-call latency on every collective — which the graph path could not hide, because the collectives are the graph. With the policy set, per-call cost dropped to reference levels (1.00 ms AllReduce, 0.70 ms AllGather) and throughput returned.

5. Secondary findings (free speed)

Once the bottleneck was gone, smaller levers became measurable — several of which had been invisible before, and one of which we had been actively fighting.

Capture 128, not 64
The model profile declares a 128-token graph-capture ceiling; we had been overriding it to 64. Restoring 128 won every cell (C8 496→542, C16 811→849) and beat the reference. The 64 was self-inflicted and masked while collectives dominated.
+17% C1 from one line
An upstream PR restores a single declaration (immutable_input_scales=True) that a migration had dropped, worth ~1.5× on MoE kernels. It was missing from every lane we ran. Applying it lifted C1 124→145 and produced our best C8 (550 alone, 580 combined with MTP3).
Shorter drafts win C1
Reducing speculative depth from 7 to 3 raised C1 by 28% (124→159), because a short draft chain is fully utilised: the adaptive verifier accepts verification depth 2.89/3 versus only 1.38/7. Depth is a latency/throughput dial, not a free win.
The intended PCIe path is not faster
The hardware profile’s b12x PCIe all-reduce measured neutral-to-worse against plain NCCL with the correct policy (+11% C1 without it). The NCCL policy was the fix; the transport choice was not.

6. The governing law

The most useful result is not the fix, it is what the fix exposed. Across every spec-decode, cost-scale, breakable-graph and tuning configuration we measured, C8 throughput landed between 537 and 580 tok/s — while acceptance ranged from 2.03 to 4.25 tokens per step.

The law. At a given concurrency, decode throughput is collective-bandwidth-bound: 
tokens/s  =  (bytes/s available to collectives) / (bytes per token)
          =  tokens/step  ×  steps/s       ← the product is invariant

This reframes optimisation. Speculative-decoding tuning cannot raise throughput on this box — it only shifts the mix (latency tails, prefill/decode balance). Exactly three levers can move the ceiling:

  1. Raise effective collective bandwidth. What the fix did: 196→542 tok/s, ~2.8×. Candidates: transport and algorithm choice, channel counts, lower-precision allreduce, or a parallel layout that ships fewer bytes.
  2. Reduce bytes per token. Anything that shrinks what each token must exchange.
  3. Reduce fixed per-step overhead. Why graphs matter so much here: eager mode is ~8 tok/s, roughly 30× worse than graph mode; capture size and graph coverage sit here.

Any future “make it faster” idea should be tested against those three. If it only changes tokens per step, expect the product to stay put.

7. Reproducing this, and the rules that made it findable

Recipe: matched A/B

  • Fix model, GPUs, client, cells, capture size, depth, scheduler limits.
  • Change one variable; measure C1×3 and C8×3 (medians), plus C4/C16.
  • Record prefill ladders too — they exposed that half the “deficit” was the same bug.

Recipe: out-of-process kernel profile

  • Launch the engine under nsys, re-exec’ing the image’s own entrypoint so configuration stays identical.
  • Run vLLM’s profiler in cuda mode; capture with --capture-range=cudaProfilerApi so only the benchmark window is recorded.
  • Normalise per wall-second; quote per-call times for collectives.

The rules

  1. Check that the launch is profile-resolved before believing any measurement. A raw launch can be ~2.8× slower for reasons no diff, commit message or config comparison will show.
  2. Never trust an A/B run under a dominant bottleneck. Quantify the bottleneck first.
  3. Profile before theorising. The answer was obvious in one kernel table and invisible in a day of code and config archaeology.
  4. Prefer cheap discriminators. “Eager on both lanes” cost one boot and localised the deficit to the graph path immediately.
  5. Read the vendor’s own mechanics. The failure mode and its remedy were both written down in the runtime’s README and profile files before we found them.

8. Caveats and corrections

  • One node, one model. All measurements are TP4 DeepSeek-V4.1-Flash on four RTX PRO 6000 (SM120) over PCIe, single node. The mechanism (profile bypass → transport mis-selection) is general; the specific numbers are not.
  • Single cells for C4/C16. C1 and C8 are medians of three cells; C4 and C16 are single 30-second cells, so differences under ~5% there are not meaningful.
  • Instrumentation costs ~25%. Configurations measured with nsys active (e.g. the capture-64 row) are floors, not rates. They are labelled as such.
  • Attribution correction. A C1 255.82 / 32K prefill 15,586 figure from an upstream PR was initially treated as a DS4.1 target. Its configuration string (“B12X-KDA”) and the PR’s six-model scope indicate it is very likely a GLM result, not DS4.1. It has been removed as a target; there is no trustworthy external DS4.1 C1 number we are aware of.
  • Unfiled defect. The newest combination (current integration tip + newest library master) deadlocks at startup on this topology, bisected to a specific library commit; the immediately preceding commit boots fine. Documented, not reported.
